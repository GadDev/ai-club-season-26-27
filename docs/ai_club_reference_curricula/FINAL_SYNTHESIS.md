# Final Synthesis

## What appears everywhere?

The unavoidable curriculum is not a list of products. It is a set of engineering questions: **What can the model do? What context does it receive? What external knowledge or tools can it use? How do we measure success? What can fail? What is it allowed to do? How do we operate it reliably?** Those questions survive model and framework churn.

Recommended protected spine:
1. LLM / model mental models.
2. Context engineering and structured interaction.
3. Retrieval / grounding basics.
4. Tool use and agent mental models.
5. Evaluation and regression thinking.
6. Security, permissions, and prompt-injection awareness.
7. Production observability, cost, and reliability.

## Where do programmes diverge?

The main philosophical forks are **understand vs ship**, **product vs platform**, **agent depth vs general AI breadth**, **research evidence vs operational reliability**, and **curriculum sequence vs experimental lab**. Those forks are exactly what the future voting system should surface rather than hiding behind one giant flat topic list.

## Which topics should be protected from popularity voting?

- LLM mental models and limitations.
- Context and data-boundary fundamentals.
- Evaluation basics.
- Security / prompt-injection basics.
- Production reliability basics before advanced autonomy.
- Any prerequisite required by a later high-interest session.

These are the vegetables. Members may not vote for broccoli, but the season still needs nutrients. 🥦

## Which topics are excellent voting candidates?

- RAG implementation variants (hybrid retrieval vs graph-assisted retrieval vs agentic retrieval).
- Coding-agent workflows and tool choices.
- MCP vs A2A vs custom APIs as an architecture debate/lab.
- Multi-agent systems vs simpler orchestration.
- Fine-tuning vs retrieval vs prompting.
- AI UX patterns.
- Model bake-offs and benchmark challenges.
- Loop engineering vs graph engineering vs deterministic workflows.

## Which topics should be unlockable?

- Multi-agent coordination after agent/tool fundamentals.
- Long-running autonomous development after coding-agent verification and security.
- Agentic RAG after retrieval evaluation.
- Advanced MCP/A2A interoperability after tool contracts and protocol basics.
- Synthetic-data loops after evaluation literacy.
- Emerging model architectures after transformer/reasoning foundations.

## Which topics should remain experimental?

Reserve spring capacity for genuinely new techniques, model architectures, agent harness patterns, interaction paradigms, and protocol extensions. Experimental does **not** mean hype slot: it means the session must state the hypothesis, evidence level, and what would falsify the claim.

## Recommended voting architecture implied by the curricula

```text
Explore themes
   ↓
Vote on meaningful alternatives
   ↓
Unlock dependent topics
   ↓
Show learning branches + prerequisites
   ↓
Let members prioritise a personal season
   ↓
Aggregate community preference
   ↓
Apply protected-core + dependency + balance rules
   ↓
Publish the coherent final season
```

### Suggested rules
- **Protected core:** editorial override for prerequisites and safety/evaluation fundamentals.
- **Diversity guardrail:** no final month should contain only one theme or only one difficulty track.
- **Dependency rule:** advanced topic cannot win a slot unless prerequisites are scheduled, already covered, or provided as pre-work.
- **Novelty budget:** cap experimental topics so the season does not age badly.
- **Continuity bonus:** give small ranking weight to topics that complete an already-popular learning chain.
- **Minority-interest protection:** allow one specialist wildcard per quarter so advanced niches are not erased by popularity voting.
- **Explainability:** every winning/losing topic should expose the reason: votes, prerequisite constraints, balance rule, or editorial protection.
